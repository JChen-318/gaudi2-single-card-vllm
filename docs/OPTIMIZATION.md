# 优化说明与实测结果

这份文档记录 2026-10-12 至 10-15 在单张 Gaudi2 上做的几轮 decode 与预热优化：瓶颈是怎么定位的、改了什么、实测效果如何、哪些尝试没有收益。所有数字都来自同一台机器，条件见各表说明；没有实测的地方会明确写「推算」或「未验证」。

- 硬件：Intel Gaudi2（HL-225，96 GiB HBM），单卡，TP=1 / PP=1
- 模型：本地命名的 Qwen3.8-27B-FP8（Qwen3.5 架构：48 层 Gated DeltaNet + 16 层全注意力），DFlash2 草稿模型，每轮 7 个草稿 token
- 采样：非 greedy（`temperature=1.0, top_p=0.95, top_k=20`），关闭 thinking
- 执行方式：`PT_HPU_LAZY_MODE=0`，eager 加 `torch.compile` 区域编译

## 1. 一轮 decode 的时间花在哪

用 vLLM 的 torch profiler 加 Habana 硬件 trace，在真实请求中途采一轮（方法和注意事项见 [tools/README.md](../tools/README.md)）。单路、短上下文：

| 组成 | 时间 | 说明 |
|---|---|---|
| 整轮 | 约 42 ms | 一轮验证 8 个 token，平均接受约 3 个 |
| 设备忙碌 | 28.3 ms | MME 15.1 ms + TPC 13.6 ms，两者基本不重叠 |
| 其中权重 GEMM | 15.0 ms | 把全部权重读一遍，约 28.75 GiB，已接近 HBM 带宽 |
| 设备空闲 | 约 13 ms | 其中约 3 ms 是内核之间的微间隙，不是在等主机 |

结论：

1. 主模型的矩阵乘已经顶到显存带宽，上下文长度和并发数都不改变这 15 ms。
2. 能动的只有两部分：随上下文增长的 KV 读取，以及设备空闲的那十来毫秒。

## 2. 长上下文为什么慢：验证 token 各读一遍上下文

这是本轮收益最大的一项。

**根因。** DFlash2 一轮验证 8 个 token。原来的 decode 输入构造把它们展平成 8 行，每行带一份完整的因果前缀页表。全注意力层用 `index_select` 取 KV（非连续分页，是拷贝），于是 16 个注意力层每层都把同一份上下文 KV 拷贝 8 遍，再各自做一次分页注意力。

每页（128 token）每层的 K+V 是 0.5 MiB，16 层合计 8 MiB。每轮 gather 的数据量是「页数 × 8」：

| 上下文 | 每轮 gather 的 KV | 去重后实际需要 |
|---|---|---|
| 7.7K | 4 GiB | 0.5 GiB |
| 30K | 16 GiB | 1.9 GiB |
| 91K | 约 45 GiB | 5.6 GiB |

对比：整个模型的权重每轮只读一遍，是 28.75 GiB。

**第二个问题：65.5K 的断崖。** 预热的最大形状只到单请求 512 页（65.5K token）。超出后分桶逻辑把块数封顶，返回的桶比真实页表小，补齐函数不再补齐，每轮形状都不同，反复现场编译。

**改法（`VLLM_HPU_SHARED_PREFIX_DECODE=1`）。** 每个请求只出一份页表，8 个验证 token 共用；每个 token 在每页上能看到几个槽位由二维的 `block_usage[页, token]` 表达。

- 主机侧：[`decode_shared_prefix.py`](../vllm-gaudi/vllm_gaudi/v1/worker/decode_shared_prefix.py) 生成页表、归属和逐 token 的可见槽位数。验证块跨页时，靠前的 token 在新页上的可见数是 0。
- 注意力：[`ops.py`](../vllm-gaudi/vllm_gaudi/extension/ops.py) 新增 `flat_pa_query_block`。查询是 `[请求, 8, hidden]`，KV 只 gather 一次。完全被掩掉的页 `block_max` 是负无穷，相减前先 clamp 到有限下界，避免出现 NaN；它的归一化权重是 0。
- 分桶：开启后 decode 桶就是「请求数 × 页数」，不再生成乘 8 的形状。把 `VLLM_DECODE_BLOCK_BUCKET_MAX` 设成 2048 即覆盖完整的 262K 上下文，桶数 45 个，和原来的 44 个基本持平。

**实测（单路）。**

| 提示词 token | 优化前每轮 | 优化后每轮 | 优化前速度 | 优化后速度 |
|---|---|---|---|---|
| 622 | 43.5–44.8 ms | 42.3 ms | 70 tok/s | 67–75 tok/s |
| 7,687 | 50.2 ms | 45.0 ms | 61.6 tok/s | 57.9 tok/s |
| 30,468 | 63.4 ms | 48.4 / 50.6 ms | 45.2 tok/s | 58.8 / 64.5 tok/s |
| 57,091 | 未测 | 57.1 ms | 未测 | 53.4 tok/s |
| 85,591 | 292 ms（91,259 token） | 62.6 ms | 9.8 tok/s | 47.6 tok/s |

- 「每轮耗时」是可比的指标。速度还取决于每轮接受了几个 token，受采样随机性影响；7.7K 那一行优化后速度反而略低，就是因为那次每轮只接受 2.61 个（优化前那次是 3.07 个）。
- 优化后每轮耗时与上下文近似线性：约 42.3 ms 加每千 token 0.24 ms。按此外推 256K 约 100 ms/轮，这是推算，没有实测。
- 优化前的长上下文数字是在散热改造之前测的，没有记录温度，不排除受过降频影响。

**设备 trace 的对照（30K，一轮）。**

| | 优化前 | 优化后 |
|---|---|---|
| 设备忙碌 | 41.3 ms | 34.8 ms |
| `gather_fwd_bf16` | 10.4 ms | 1.7 ms |
| 注意力 BatchGemm | 10.7 ms | 4.5 ms |
| 权重 GEMM | 15.3 ms | 15.4 ms |

gather 降了 6 倍。BatchGemm 没有降 8 倍，因为 8 个 token 对每页的乘法运算量不变，省掉的只是重复读取。

## 3. 主机侧的 decode 输入准备

每轮开始前，主机要为 48 个 GDN 层算状态索引，为 4 个注意力 KV 组各建一份页表。原实现是 Python 列表循环，耗时随上下文增长。

改法（`VLLM_HPU_FAST_DECODE_PREP=all`）：[`decode_fast_paths.py`](../vllm-gaudi/vllm_gaudi/v1/worker/decode_fast_paths.py) 用 numpy 向量化。上线方式是自检式的：预热的每一轮和上线后的前 N 轮（`VLLM_HPU_FAST_DECODE_PREP_VERIFY`）同时算快慢两条路径并逐元素比较，全部一致才切到快速路径；出现任何不一致就在本进程内永久退回原实现。

服务器 CPU 上的微基准（参考实现 → 快速路径）：

| 场景 | 注意力组页表 |
|---|---|
| 1K 上下文，B=2 | 1.05 → 0.72 ms |
| 32K 上下文，B=1 | 3.75 → 0.88 ms |
| 200K 上下文，B=2 | 43.6 → 1.9 ms |

连同「并发上限从 4 降到 2」「环境变量读取缓存」一起上线后：单路短上下文每轮 43.5–44.8 → 41.9–42.5 ms；2 路并发每轮约 64 → 51–55 ms。这三项没有分别做消融。

## 4. 两处断图

用 `TORCH_LOGS=graph_breaks` 启动后在日志里定位，再在 CPU 上用同版本 torch 复现。

**候选选择器。** `flashinfer_gaudi` 的 `top_k`、`select_path` 等函数会查询策略清单，清单通过 `lru_cache` 包着的函数读取。Dynamo 会穿透缓存装饰器去追踪 `importlib.resources`，里面的 singledispatch 用类做弱引用字典的键，追不下去，于是每个调用点断一次图，日志里对应 10 个碎片帧。改成导入时读一次、存模块级字典后消失。复现与检查：[`validation/dynamo/check_selector_graph.py`](../validation/dynamo/check_selector_graph.py)。

**drafter 注意力（只在 2 路并发时）。** 模型适配器把提示阶段 `block_list` 的长度标成无后备值的符号维度。见过第二种 batch 大小后 batch 维也变成符号，Habana FusedSDPA 包装函数里的 `k.numel() == 0` 成了 Dynamo 判断不了的表达式，每次注意力调用断一次图。`VLLM_HPU_SKIP_UNBACKED_BLOCK_LIST=1` 跳过这个标记。复现：[`validation/dynamo/repro_fsdpa_unbacked.py`](../validation/dynamo/repro_fsdpa_unbacked.py)。

两处在真机日志里都确认消失，drafter 模型阶段的主机耗时在 2 路并发时从十几毫秒降到 4.2 ms，与单路相同。**但整轮时间没有相应缩短**，见下一节。

## 5. 没有带来收益或没有证实的事项

如实记录，避免重复踩坑。

| 事项 | 结果 |
|---|---|
| 修掉两处断图 | 断图消失、drafter 阶段主机耗时下降，但 2 路并发每轮耗时基本不变（53.2 → 52.2 ms，在波动范围内）。此前「可省 8–10 ms」的估计依据的是更早版本的 trace，没有兑现 |
| 4 个注意力组共用掩码（`VLLM_HPU_SHARE_GROUP_MASKS=1`） | 每轮少约 18 个零散设备算子，但主模型前向开头的空闲没有变小，整轮耗时不变 |
| Dynamo 守卫筛选 | 单独删参数守卫和静态守卫都没有可测的收益 |
| drafter 用 `dynamic=False` 静态编译 | 启动即失败（无后备值符号没有具体值），已弃用 |
| 主模型编译区域的缓存查找（每轮 25 次共 9.3 ms） | 原因后来查清（见第 9 节）：19 个层组共用一个代码对象，查找要先在兄弟组的条目上失败；改成独立代码对象后查找变快，但每组仍约 0.4 ms 的守卫检查 |
| 预录重放 | 独立实验没有显示净提速 |
| 稳态解码跳过守卫检查（v11，`VLLM_HPU_GUARD_SKIP`） | 主模型提交的主机时间 13.7 → 9.2 ms，但整轮不变：v11 之后主机已不在关键路径上（见第 11 节） |
| 采样随机数池（v11，`VLLM_HPU_RNG_POOL`） | 采样提交 3.2 → 1.25 ms，整轮同样不变 |
| 下一轮小 H2D 合并成一次 | 未做：此前实测按 dtype 打包反而慢约 3 倍，单次小 H2D 约 17 µs |
| ~~异步准备下一轮不在关键路径上~~ | 这个判断是错的：第 9 节的「下一轮预提交」单路省 2.5 ms、两路省 2.8 ms |

## 6. 正确性验证做了什么、没做什么

- 离线：[`validation/`](../validation/) 下 2609 项 CPU 测试（第 9 节的改动 84 项，第 11 节 21 项）。被测代码按 AST 从本仓库源码里抽出，不是重写的副本。共享前缀注意力与原展平布局在 float64 下一致到 1e-9，另有独立的朴素 softmax 对照、跨页用例、bf16/float32、真实头数形状。
- 真机：先用 `VLLM_SKIP_WARMUP=true` 做冒烟（约 6 分钟可用），再带完整预热。冒烟抓到过一个离线测试没覆盖的问题（返回的张量内存不连续），已修并补了测试。
- 2 路并发：新开关全开与全关（同一份代码）相比，4 组输出共 800 个 token 逐字相同。
- 单路：`temperature=0` 下同一个服务重跑也不逐字一致（5 组里 3 组不同），所以单路没法用逐字比对来判定；原因未查。
- 这个部署的请求守卫拒绝 logprobs 请求，做不了逐 token 的数值比对。
- 长上下文：30K 和 86K 各取了一段 `temperature=0` 输出，内容通顺切题；没有做长上下文的逐字对照。
- 下一轮预提交：测量期间复用 3000 多次，「预测与实际调度不一致」0 次；不一致时会报错并关闭该功能，绝不重跑同一轮。
- 增量准备：上线后前 64 轮同时跑完整准备，逐字段比对全部一致。
- 草稿提前：上线后前 32 轮同时跑原主机草稿路径，32/32 行草稿完全一致；离线另有设备桥接与主机路径逐 slot 一致的测试（所有接受长度、有无滑窗、单/两路）。
- FP8 词表投影：与 BF16 对照 6057 行，top-1 一致 98.4%，平均 KL 0.0016。
- 未做：工具调用、流式中途取消、抢占、256K 实测、多日稳定性。

## 7. prefill（首 token 时间）现状

没有优化过，只有测量：

| 提示词 token | 首 token 时间 | 平均速度 |
|---|---|---|
| 7,687 | 1.8 秒 | 约 4,300 tok/s |
| 30,468 | 7.0 秒 | 约 4,350 tok/s |
| 57,091 | 16.9 秒 | 约 3,400 tok/s |
| 85,591 | 32.1 秒 | 约 2,700 tok/s |

越长越慢，从配置和代码看有三层原因（没有采过 prefill 的设备 trace，占比未知）：

1. 提示词按 2048 token 分块，每块都要对前面全部上下文做注意力，总时间带平方项。
2. prefill 的上下文页数桶按倍数跳（…255、509、1017、2047 页），超过 65K 的上下文按 130K 计算，超过 130K 按 262K 计算。
3. 每块对历史 KV 有 gather 和拼接两遍拷贝；掩码矩阵是 2048 ×（上下文 + 2048），4 个注意力组各建一份。

另有一处已定位未处理的断图：GDN 层 prefill 路径里的 `_preprocess_qk_l2norm` 被显式禁止编译。

## 8. 还可以做的方向

| 方向 | 场景 | 预期（推算） | 把握 |
|---|---|---|---|
| 提高每轮接受数（例如同时验证候选树里的多条路径） | 自然语言文本 | 文本速度可能 +30% 以上 | 研究性质，未验证 |
| 主模型层组 19 → 8–16 个 | 单路 | 0.5–1.5 ms/轮 | 中 |
| KV cache 改 FP8 | 长上下文 | 3 万 token 约 −3 ms/轮，越长越明显 | 中，需评估质量 |
| prefill 上下文桶改细、加大分块 | 长提示词首 token | 可能 −30–50% | 中 |
| FP8 词表投影开/关的接受率对照 | 全部 | 排除它降低接受率的可能 | 需要一次重启 |

| 抓一次 v11 的设备 trace | 单路 | 定位每轮剩余约 4 ms 的设备空闲 | 需要一次带 profiler 的重启 |

v11 之后单路短上下文每轮 27.6 ms，设备忙约 23 ms（v7 trace 的值，v11 未重测），主机每轮有约 13.8 ms 在等设备。继续提速要靠设备侧或提高接受数，主机侧已不是瓶颈。

## 9. v6–v10：压缩每轮的主机串行时间

v5 之后，单路一轮约 42 ms，设备忙碌只有 28 ms。逐段对照设备空闲时主机在做什么，问题集中在三处：一轮开头提交前几个编译区域、采样读回之后准备草稿、两轮之间准备下一轮输入。以下改动都是默认关闭的独立开关，启动示例见 [examples/launcher-v10.example.sh](../examples/launcher-v10.example.sh)。

### 9.1 改了什么

| 开关 | 做什么 |
|---|---|
| `VLLM_HPU_UNIQUE_COMPILE_CODE` | 每个编译区域换成只属于自己的 forward 代码对象。Dynamo 按代码对象缓存并逐条检查，19 个层组共用一个 forward 时，每次查找都要先在兄弟组的条目上失败。本地微基准 19 个实例时查找从 18 µs 降到 1.6 µs |
| `VLLM_HPU_DFLASH2_DRAFT_STACK` | 草稿模型的嵌入、5 层、norm 编译成一个区域 |
| `VLLM_HPU_FUSED_MODEL_ENTRY` | 嵌入并入第一个层组；注意力元数据和 rotary 表合成一个编译区域 |
| `VLLM_HPU_DFLASH2_LOOKAHEAD` | **下一轮预提交**：草稿提交后，按预测的下一步（同一批请求、每个 8 个 token、草稿即本轮输出）准备输入并提交下一轮主模型，下一步核对请求、位置、草稿、页表后直接复用。只有一路结束而另一路继续时，从两路结果里取出继续那一路的行，绝不重跑（主模型会推进 GDN 状态） |
| `VLLM_HPU_DFLASH2_LOOKAHEAD_SAMPLE` | 预提交主模型后接着提交该轮的拒绝采样 |
| `VLLM_HPU_DFLASH2_LOOKAHEAD_DELTA` | **增量准备**：请求和页列表不变时，下一轮输入由上一轮增量得到，只重算位置（含 M-RoPE）、4 个注意力组的 slot、页使用量和接受数；不变的张量直接复用。前 64 次与完整准备逐字段比对 |
| `VLLM_HPU_FAST_TOPK_TOPP` | 采样的 top-k/top-p 不再整词表排序：先取每块 256 个词的最大值，选出可能包含前 64 名的块，再在这些块里取 top-k。k ≤ 64 且 0 < p ≤ 1 时启用 |
| `VLLM_HPU_DFLASH2_CHUNKED_TOPK` | 草稿候选 top-16 用同样的两级取法 |
| `VLLM_HPU_LM_HEAD_FP8` | 词表投影（248K × 5120，每轮读两次）按输出通道量化为 FP8 |
| `VLLM_HPU_DFLASH2_DIRECT_CHECKPOINTS`（已有，此前未启用） | GDN 8 个检查点直接写入状态池 |
| `VLLM_HPU_DFLASH2_PAGE_BUCKETS` | 草稿的上下文页数补齐到桶，避免每多一页就现场编译一次 |
| `VLLM_HPU_STEP_TIMER`、`VLLM_HPU_V6_CONTROL` | 每轮时间戳和阶段标记；同一进程内切换运行期开关做 A/B |

另修了一处启用条件：草稿的几条快速路径要求「没有碎片整理器」，但运行器总会创建一个关闭状态的碎片整理器，这些路径此前一直没走。

| | v5 | v6 |
|---|---:|---:|
| 设备忙碌合计 | 28.3 ms | 23.1 ms |
| 权重 GEMM | 15.0 | 13.9（FP8 词表投影） |

### 9.3 实测（同进程切换开关，每轮中位数）

| 场景 | v5 | v6 | v8 | v10（生产配置） |
|---|---:|---:|---:|---:|
| 单路短上下文 | 42.3 ms | 34.4 | 31.0 | **30.4–30.6** |
| 两路并发 | 52.2（均值） | 42.1 | 36.0–36.5 | **35.6** |
| 单路 3 万 token | 48.4–50.6 | 40.4 | 37.3 | **37.3** |

v6–v8 在带 profiler 的测试版上测，v10 是生产配置。逐项拆分（单路）：

| 项 | 每轮 |
|---|---:|
| 启动期生效的几项合计（独立代码对象、草稿合一、入口合并、候选 top-k、FP8 词表投影、检查点直写） | −3.5 ms |
| 快速 top-k/top-p | −1.7 ms |
| 下一轮预提交 | −2.5 ms（两路 −2.8 ms） |
| 增量准备 | −3.0 ms（两路 −2.9 ms） |
| 生产配置 + 草稿快速路径真正生效 + 页数分桶 | −0.6 ms |

**没有收益的尝试**：采样提前提交、在单路上打开草稿 CPU 输入打包（那时快速路径并未真正启用）、把下一轮准备挪到草稿之前。原因都是这些主机时间本来就和设备执行重叠，不在关键路径上。

### 9.4 编译结果磁盘缓存

`PT_HPU_RECIPE_CACHE_CONFIG` 要求 `GC_KERNEL_PATH` 是单个文件，而本项目要加载三个 TPC 内核库，直接打开会导致引擎初始化失败。为此写了单文件转接层 [native/tpc-kernel-shim](../native/tpc-kernel-shim/)，合并 3261 个内核并按 GUID 转发。转接层下完整预热和测速正常。首次带缓存的预热仍为 2661 秒、写入约 860 MB，缓存对重启时间的收益还没有测。

注意：v6 之后完整预热从约 1750 秒变成约 2650 秒，原因未查。

## 11. v11：草稿不再等主机读回

v10 的单路一轮里，读回接受结果之后要串行经过「下一轮输入准备 1.3 ms → 草稿准备与提交 2.5 ms → 主模型前几组提交」，这段时间设备基本空闲。草稿模型其实不需要主机知道接受了几个 token：拒绝采样的输出是定宽的（未接受的位置为 −1），接受数、位置、KV slot 和注意力偏置都可以在设备上算出来。以下开关默认关闭，启动示例见 [examples/launcher-v11.example.sh](../examples/launcher-v11.example.sh)。

### 11.1 改了什么

| 开关 | 做什么 |
|---|---|
| `VLLM_HPU_DFLASH2_PREDRAFT`（`_VERIFY`=32） | **草稿提前**：提前提交下一轮主模型和采样后，紧接着用 FlashInfer-Gaudi 的设备侧桥接提交该轮的草稿模型。桥接准备、上下文特征投影和草稿 KV 写入合成一个编译区域；上下文页从最早可能的查询起点按滑窗往前取，多出的位置由偏置屏蔽。下一步复用这一轮时直接取用草稿，不再在读回之后跑主机草稿路径。前 32 轮与主机草稿逐行比对；预热时为每个解码桶编译；出现异常只关闭这一项 |
| `VLLM_HPU_GUARD_SKIP`（`_WARM`=3） | 提前提交窗口内用 `torch.compiler.set_stance(skip_guard_eval_unsafe=True)`。轮次键包含所有输入的形状、元数据标志、运行期开关、采样标志和草稿页桶；同一个键连续 3 轮完整守卫检查都没有产生新图才跳过，每 1024 轮复查一次。仍需重编译的区域会在执行前报错，由区域包装用完整守卫重试这一次调用，不会重复执行 |
| `VLLM_HPU_RNG_POOL`（=32） | 拒绝采样的均匀随机数和指数噪声一次生成 32 轮，每轮取一份独立拷贝。HPU 上每个 eager 随机算子约 1–2 ms 主机时间，大多是固定开销。带独立随机数生成器的请求不走池 |

## 12. v11b–v11d：提前读回与引擎线程隔离

v11 的设备 trace（单路一轮，带 profiler）：跨度 28.3 ms，设备忙 23.1 ms（矩阵乘 13.9、融合逐元素 3.5、GDN 3.0、其他逐元素 2.3、gather 1.4）。空闲的 5.2 ms 包括两部分：约 3200 个小于 20 µs 的算子间隙，共 3.2 ms；以及一轮开头约 2.0 ms，从主机开始提交入口区域到主模型第一组开跑。两路：跨度 32.7 ms，忙 27.4 ms。主模型各组、采样、草稿之间已经首尾相接。

| 开关 | 做什么 |
|---|---|
| `VLLM_HPU_DFLASH2_EARLY_READBACK` | **提前读回**：采样提交后，立即在同一个流上把预采样结果拷到固定内存（两块交替，配一个事件），下一步直接读这份拷贝，不再排在提前提交的草稿之后。前 16 次与设备上的值比对。运行期可由 `control.json` 的 `early_readback` 切换 |
| `VLLM_HPU_PIN_MAIN_CPU`（=CPU 编号） | **引擎线程隔离**：预热结束后把引擎主线程固定到一个核上，进程里其他线程（约 290 个）都避开这个核及其超线程兄弟；批次变化时再处理一次新线程 |

- 第一版提前读回用旁路流，反而更慢（单路 28.3 vs 27.7 ms）。原来的读回确实在等草稿（「进入 → 读回」从 13.9 ms 降到 9.3 ms），但之后主机的每一步都均匀慢了约 25%。
- 原因是 CPU 放置：引擎进程里 Habana 运行时的 AccThreadPool 线程一直 100% 占用 CPU 轮询，主线程和它落在同一个物理核的两个超线程上时，就会互相争用。同进程对照：把主线程隔离后，提前读回开启 27.49 ms、关闭 27.75 ms；恢复原来的亲和性，立即又变成开启 28.29 ms、关闭 27.87 ms。
- v11d 生产版（隔离 + 提前读回，同进程，每轮中位数）：单路 27.46 / 27.60 ms（关闭提前读回 27.80 / 27.71），两路 31.50–31.76 ms，3 万 token 33.62 ms。提前读回在隔离之后只省 0.2–0.3 ms。
- 此时设备侧下限约 26.3 ms（忙 23.1 + 算子间隙 3.2）。要继续提速，主要靠设备侧（算子数量、GDN、矩阵乘）或接受率。

## 13. v12：GDN 递推 kernel 重写

单路一轮设备忙 23.1 ms 中，GDN 核心占 4.6 ms，其中递推 kernel 2.97 ms（两路 5.85 ms），每层 62 µs。按读写的数据量，带宽只需要约 2.5 µs；真正的瓶颈是每行、每个 token 两次 6 级跨通道归约，约占向量指令的 63%。

用 Habana 自带的 TPC 模拟器（`libtpcsim_shared` + `tpc_tests::RunSimulation`）在 CPU 上逐周期运行完整 kernel：原 kernel 2,495,280 周期，分到 24 个 TPC 约 63 µs/层，与 trace 吻合。新 kernel 见 [native/gdn-fused-kernel](../native/gdn-fused-kernel/README.md)：

- 每块 8 行，16 个点积共用一棵交错归约树，结果落在同一个向量的 16 个通道：1,298,056 周期（1.92×）。试过的其他变体（每块 4 行、标量门控、边算边合并）都更慢。
- 融合 kernel（新算子 `custom_op::flashinfer_gaudi_gdn_mtp_fused`）：选检查点槽位、q/k 的 L2 归一化（只算系数）、`exp`、BF16 转换都在 kernel 里完成，每个工作项的准备只做一次。单路 1,256,454 周期，两路 2,512,908。
- 真机数值：单路、两路各 4 组随机数据，与 PyTorch 参考路径一致（输出差 ≤ 6.1e-5，状态差约 1e-7）。单次调用（一层，两路）：旧 0.194 ms → 新 0.137 ms。单路的单次调用被主机启动开销遮住（各路线都是 0.128–0.136 ms）。
- 开关 `FLASHINFER_GAUDI_MTP_FUSED=1`（需要重新编译并打过补丁的 flashinfer_gaudi，换库后要清编译缓存）。

| 场景（生产配置，每轮中位数） | v11d | v12 |
|---|---:|---:|
| 单路短上下文 | 27.46 / 27.60 ms | **26.55–26.66** |
| 两路并发 | 31.50–31.76 | **30.71–30.73**（290–310 tok/s） |
| 单路 3 万 token | 33.62 | **32.73** |

整轮只快了约 0.9 ms，比按单次调用推算的 2–4 ms 少，原因见第 15 节。

## 14. v12c / v13：FP8 KV 缓存，预热从 48 分钟缩短到 23 分钟

### 14.1 FP8 KV 缓存

`--kv-cache-dtype fp8_inc`，同时去掉 `QUANT_CONFIG`（不做校准，用默认缩放），同样 28 GiB 的 KV 预算：

- 容量从 262,144 token 增加到 527,301 token（同时容纳两个 256K 请求），`VLLM_DECODE_BLOCK_BUCKET_MAX` 相应改为 4096，decode 分桶从 45 个增加到 61 个。
- 速度（生产配置，每轮中位数）：单路 26.70 ms，两路 30.67 ms（294 tok/s），3 万 token **30.66 ms**（BF16 KV 为 32.73 ms，注意力读取的数据减半）。带 profiler 的测试版在约 10 万 token 上下文测得 38.46 ms/轮（75 tok/s）。
- 接受率（每轮 4.4–5.2 个 token，3 万 token 约 3 个）与 BF16 时相当，greedy 输出正常。**没有做系统的质量评测**：未校准的 FP8 KV 在更长上下文或其他任务上是否有损失，未验证。

### 14.2 预热时间

v12c 的预热耗时 2887 秒。用 `VLLM_HPU_COMPILE_TIMES=1` 统计编译：Dynamo `compile_inner` 1051 秒（字节码追踪 472、后端 490，其中 Habana 后端优化 pass 139），Synapse 图编译 5405 次只用 7.9 秒（全部命中 recipe 缓存）。约 64% 的时间不在这些计时器里。

用 py-spy（`--native --idle`，10 Hz）对预热采样（采样会让预热变慢约 1.45 倍，各部分占比仍可信）：

| 主线程时间去向 | 占比 |
|---|---:|
| `HabanaMemoryProfiler` 进出时的 `gc.collect()` | **32%** |
| Dynamo 后端：AOT autograd（含 Habana pass） | 36% |
| Dynamo 字节码追踪 | 21% |
| 加载权重、构建守卫、其他 | 约 10% |
| 执行图、Synapse 编译 | ≈ 0 |

每个预热分桶都包在一个 `HabanaMemoryProfiler` 里，进入和退出时各做一次全量 `gc.collect()`。编译了几百个图之后，进程里有上百万个 Dynamo/FX 对象，每次 gc 要 2.5–4 秒，而测得的显存增量只用来打一行日志。

| 开关 | 做什么 |
|---|---|
| `VLLM_HPU_WARMUP_PHASE_GC` | 每个分桶只读显存用量、不做 gc；只在 prompt 预热和 decode 预热两个阶段的开始与结束各 gc 一次 |
| `VLLM_HPU_COMPILE_TIMES` | 预热结束后在日志里打印编译时间分解（Dynamo 各阶段、Habana pass、Synapse 编译） |

结果：预热 2887 → **1361 秒**（prompt 21.4 → 11.3 分钟，decode 22.5 → 9 分钟），从重启到恢复服务约 28 分钟；运行速度不变（单路 26.8 ms，两路 30.75 ms，3 万 token 30.60 ms）。

剩下的预热基本都是主机端 Python 编译（`compile_inner` 约 1050 秒，500 个图）。`TORCH_LOGS=recompiles` 显示 354 次重新编译：133 次是 token 维从静态转为动态（每个编译区域第一次按固定长度编译，遇到第二种长度时再编一次），提前标记成动态可以省掉（推算约 4–5 分钟，未验证）；约 112 次来自 `block_list` / `block_mapping` 长度 0/1 的特化、`attn_bias` 在 None 与张量之间切换，以及 `attn_bias` 的维度变化，对应的是不同的代码路径；其余来自采样器、GDN prefill 和草稿。Python 端的编译结果无法跨重启复用：PyTorch 的编译缓存只支持 inductor 后端，不支持 `hpu_backend`。启动示例见 [examples/launcher-v14.example.sh](../examples/launcher-v14.example.sh)。

## 15. v14：去掉融合 GDN kernel 之后的检查点复制

第 13 节的融合 kernel 整轮只快了约 0.9 ms。对比 v11 与 v12 的设备 trace（单路，每轮）：

| | v11 | v12 |
|---|---:|---:|
| GDN 核心 | 4.62 ms | 3.36 ms |
| `out_proj` GEMM | 0.73 | 1.17 |
| 内部 DMA 复制 | 0.48 | 2.41 |
| 设备忙合计 | 23.09 | 22.49 |

融合 kernel 本身达到预期（每层 62 → 44 µs），但每个 GDN 层在它之后多了一次约 25 MB 的内部 DMA 复制，把 8 个检查点从 kernel 输出拷进状态池。这些复制与紧接着的 norm、量化和 `out_proj` GEMM 同时进行，争用 HBM 带宽：这几个节点都慢了约 1.5 倍（GEMM 每次 15 → 23 µs），两路时 MLP 也被拖慢。

原因：prepared 路线先 `index_select` 取出初始状态，kernel 不读状态池，图编译器可以让 kernel 直接把检查点写进池里；融合 kernel 在内部按槽位读 `state_pool`，同一个张量既被读又被写，编译器只能先写临时缓冲再复制。

| 开关 | 做什么 |
|---|---|
| `FLASHINFER_GAUDI_MTP_FUSED_GATHER`（默认开） | 融合路线先 `index_select` 取出各请求的初始状态，作为 kernel 的「池」传入，槽位索引都指向本请求自己那一行。kernel 计算不变，状态池在这一步只被写入 |

结果（生产配置，每轮中位数）：

| 场景 | v13 | v14 |
|---|---:|---:|
| 单路短上下文 | 26.81 ms | **26.17 / 26.28** |
| 两路并发 | 30.75 | **29.69**（312 tok/s） |
| 单路 3 万 token | 30.60 | **30.17** |

greedy 输出与之前一致。离线验证用一个与 kernel 约定相同的 Python 替身，确认两条路线的输出和状态池逐位相同（`validation/test_v13_fused_gather.py`）。

同时打开了 Dynamo 本地 PGO（`TORCH_COMPILE_JOB_ID` + `TORCHINDUCTOR_CACHE_DIR`）：每次编译后把各函数哪些维度是动态的写到磁盘，下次启动时第一次编译就按动态形状进行，预计可省掉第 14.2 节那 133 次「静态转动态」的重新编译。效果要到下一次重启才能确认，未验证。这次 GDN 相关的图有变化，设备端 recipe 需要重新编译，预热 1539 秒。

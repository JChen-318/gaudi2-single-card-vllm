# 优化说明与实测结果

这份文档记录 2026-10-12 至 10-14 在单张 Gaudi2 上做的一轮 decode 优化：瓶颈是怎么定位的、改了什么、实测效果如何、哪些尝试没有收益。所有数字都来自同一台机器，条件见各表说明；没有实测的地方会明确写「推算」或「未验证」。

- 硬件：Intel Gaudi2（HL-225，96 GiB HBM），单卡，TP=1 / PP=1
- 模型：本地命名的 Qwen3.8-27B-FP8（Qwen3.5 架构：48 层 Gated DeltaNet + 16 层全注意力），DFlash2 草稿模型，每轮 7 个草稿 token
- 采样：非 greedy（`temperature=1.0, top_p=0.95, top_k=20`），关闭 thinking
- 执行方式：`PT_HPU_LAZY_MODE=0`，eager 加 `torch.compile` 区域编译

## 1. 一轮 decode 的时间花在哪

用 vLLM 的 torch profiler 加 Habana 硬件 trace，在真实请求中途采一轮（方法和注意事项见 [tools/README.md](../tools/README.md)）。单路、短上下文：

| 组成 | 时间 | 说明 |
|---|---|---|
| 整轮 | 约 42 ms | 一轮验证 8 个 token，平均接受约 3 个 |
| 设备忙碌 | 28.3 ms | MME 15.1 ms + TPC 13.6 ms，两者基本不重叠 |
| 其中权重 GEMM | 15.0 ms | 把全部权重读一遍，约 28.75 GiB，已接近 HBM 带宽 |
| 设备空闲 | 约 13 ms | 其中约 3 ms 是内核之间的微间隙，不是在等主机 |

结论：

1. 主模型的矩阵乘已经顶到显存带宽，上下文长度和并发数都不改变这 15 ms。
2. 能动的只有两部分：随上下文增长的 KV 读取，以及设备空闲的那十来毫秒。

## 2. 长上下文为什么慢：验证 token 各读一遍上下文

这是本轮收益最大的一项。

**根因。** DFlash2 一轮验证 8 个 token。原来的 decode 输入构造把它们展平成 8 行，每行带一份完整的因果前缀页表。全注意力层用 `index_select` 取 KV（非连续分页，是拷贝），于是 16 个注意力层每层都把同一份上下文 KV 拷贝 8 遍，再各自做一次分页注意力。

每页（128 token）每层的 K+V 是 0.5 MiB，16 层合计 8 MiB。每轮 gather 的数据量是「页数 × 8」：

| 上下文 | 每轮 gather 的 KV | 去重后实际需要 |
|---|---|---|
| 7.7K | 4 GiB | 0.5 GiB |
| 30K | 16 GiB | 1.9 GiB |
| 91K | 约 45 GiB | 5.6 GiB |

对比：整个模型的权重每轮只读一遍，是 28.75 GiB。

**第二个问题：65.5K 的断崖。** 预热的最大形状只到单请求 512 页（65.5K token）。超出后分桶逻辑把块数封顶，返回的桶比真实页表小，补齐函数不再补齐，每轮形状都不同，反复现场编译。

**改法（`VLLM_HPU_SHARED_PREFIX_DECODE=1`）。** 每个请求只出一份页表，8 个验证 token 共用；每个 token 在每页上能看到几个槽位由二维的 `block_usage[页, token]` 表达。

- 主机侧：[`decode_shared_prefix.py`](../vllm-gaudi/vllm_gaudi/v1/worker/decode_shared_prefix.py) 生成页表、归属和逐 token 的可见槽位数。验证块跨页时，靠前的 token 在新页上的可见数是 0。
- 注意力：[`ops.py`](../vllm-gaudi/vllm_gaudi/extension/ops.py) 新增 `flat_pa_query_block`。查询是 `[请求, 8, hidden]`，KV 只 gather 一次。完全被掩掉的页 `block_max` 是负无穷，相减前先 clamp 到有限下界，避免出现 NaN；它的归一化权重是 0。
- 分桶：开启后 decode 桶就是「请求数 × 页数」，不再生成乘 8 的形状。把 `VLLM_DECODE_BLOCK_BUCKET_MAX` 设成 2048 即覆盖完整的 262K 上下文，桶数 45 个，和原来的 44 个基本持平。

**实测（单路）。**

| 提示词 token | 优化前每轮 | 优化后每轮 | 优化前速度 | 优化后速度 |
|---|---|---|---|---|
| 622 | 43.5–44.8 ms | 42.3 ms | 70 tok/s | 67–75 tok/s |
| 7,687 | 50.2 ms | 45.0 ms | 61.6 tok/s | 57.9 tok/s |
| 30,468 | 63.4 ms | 48.4 / 50.6 ms | 45.2 tok/s | 58.8 / 64.5 tok/s |
| 57,091 | 未测 | 57.1 ms | 未测 | 53.4 tok/s |
| 85,591 | 292 ms（91,259 token） | 62.6 ms | 9.8 tok/s | 47.6 tok/s |

- 「每轮耗时」是可比的指标。速度还取决于每轮接受了几个 token，受采样随机性影响；7.7K 那一行优化后速度反而略低，就是因为那次每轮只接受 2.61 个（优化前那次是 3.07 个）。
- 优化后每轮耗时与上下文近似线性：约 42.3 ms 加每千 token 0.24 ms。按此外推 256K 约 100 ms/轮，这是推算，没有实测。
- 优化前的长上下文数字是在散热改造之前测的，没有记录温度，不排除受过降频影响。

**设备 trace 的对照（30K，一轮）。**

| | 优化前 | 优化后 |
|---|---|---|
| 设备忙碌 | 41.3 ms | 34.8 ms |
| `gather_fwd_bf16` | 10.4 ms | 1.7 ms |
| 注意力 BatchGemm | 10.7 ms | 4.5 ms |
| 权重 GEMM | 15.3 ms | 15.4 ms |

gather 降了 6 倍。BatchGemm 没有降 8 倍，因为 8 个 token 对每页的乘法运算量不变，省掉的只是重复读取。

## 3. 主机侧的 decode 输入准备

每轮开始前，主机要为 48 个 GDN 层算状态索引，为 4 个注意力 KV 组各建一份页表。原实现是 Python 列表循环，耗时随上下文增长。

改法（`VLLM_HPU_FAST_DECODE_PREP=all`）：[`decode_fast_paths.py`](../vllm-gaudi/vllm_gaudi/v1/worker/decode_fast_paths.py) 用 numpy 向量化。上线方式是自检式的：预热的每一轮和上线后的前 N 轮（`VLLM_HPU_FAST_DECODE_PREP_VERIFY`）同时算快慢两条路径并逐元素比较，全部一致才切到快速路径；出现任何不一致就在本进程内永久退回原实现。

服务器 CPU 上的微基准（参考实现 → 快速路径）：

| 场景 | 注意力组页表 |
|---|---|
| 1K 上下文，B=2 | 1.05 → 0.72 ms |
| 32K 上下文，B=1 | 3.75 → 0.88 ms |
| 200K 上下文，B=2 | 43.6 → 1.9 ms |

连同「并发上限从 4 降到 2」「环境变量读取缓存」一起上线后：单路短上下文每轮 43.5–44.8 → 41.9–42.5 ms；2 路并发每轮约 64 → 51–55 ms。这三项没有分别做消融。

## 4. 两处断图

用 `TORCH_LOGS=graph_breaks` 启动后在日志里定位，再在 CPU 上用同版本 torch 复现。

**候选选择器。** `flashinfer_gaudi` 的 `top_k`、`select_path` 等函数会查询策略清单，清单通过 `lru_cache` 包着的函数读取。Dynamo 会穿透缓存装饰器去追踪 `importlib.resources`，里面的 singledispatch 用类做弱引用字典的键，追不下去，于是每个调用点断一次图，日志里对应 10 个碎片帧。改成导入时读一次、存模块级字典后消失。复现与检查：[`validation/dynamo/check_selector_graph.py`](../validation/dynamo/check_selector_graph.py)。

**drafter 注意力（只在 2 路并发时）。** 模型适配器把提示阶段 `block_list` 的长度标成无后备值的符号维度。见过第二种 batch 大小后 batch 维也变成符号，Habana FusedSDPA 包装函数里的 `k.numel() == 0` 成了 Dynamo 判断不了的表达式，每次注意力调用断一次图。`VLLM_HPU_SKIP_UNBACKED_BLOCK_LIST=1` 跳过这个标记。复现：[`validation/dynamo/repro_fsdpa_unbacked.py`](../validation/dynamo/repro_fsdpa_unbacked.py)。

两处在真机日志里都确认消失，drafter 模型阶段的主机耗时在 2 路并发时从十几毫秒降到 4.2 ms，与单路相同。**但整轮时间没有相应缩短**，见下一节。

## 5. 没有带来收益或没有证实的事项

如实记录，避免重复踩坑。

| 事项 | 结果 |
|---|---|
| 修掉两处断图 | 断图消失、drafter 阶段主机耗时下降，但 2 路并发每轮耗时基本不变（53.2 → 52.2 ms，在波动范围内）。此前「可省 8–10 ms」的估计依据的是更早版本的 trace，没有兑现 |
| 4 个注意力组共用掩码（`VLLM_HPU_SHARE_GROUP_MASKS=1`） | 每轮少约 18 个零散设备算子，但主模型前向开头的空闲没有变小，整轮耗时不变 |
| Dynamo 守卫筛选 | 单独删参数守卫和静态守卫都没有可测的收益 |
| drafter 用 `dynamic=False` 静态编译 | 启动即失败（无后备值符号没有具体值），已弃用 |
| 主模型编译区域的缓存查找（每轮 25 次共 9.3 ms） | 怀疑 19 个层组共用一个代码对象导致查找变慢，本地基准没能证实，原因未明 |
| 主模型分组合并、预录重放、异步准备下一轮 | 主模型设备时间已到带宽下限，主机提交不在关键路径上；预录重放的独立实验也没有显示净提速 |

## 6. 正确性验证做了什么、没做什么

- 离线：[`validation/`](../validation/) 下 2504 项 CPU 测试。被测代码按 AST 从本仓库源码里抽出，不是重写的副本。共享前缀注意力与原展平布局在 float64 下一致到 1e-9，另有独立的朴素 softmax 对照、跨页用例、bf16/float32、真实头数形状。
- 真机：先用 `VLLM_SKIP_WARMUP=true` 做冒烟（约 6 分钟可用），再带完整预热。冒烟抓到过一个离线测试没覆盖的问题（返回的张量内存不连续），已修并补了测试。
- 2 路并发：新开关全开与全关（同一份代码）相比，4 组输出共 800 个 token 逐字相同。
- 单路：`temperature=0` 下同一个服务重跑也不逐字一致（5 组里 3 组不同），所以单路没法用逐字比对来判定；原因未查。
- 这个部署的请求守卫拒绝 logprobs 请求，做不了逐 token 的数值比对。
- 长上下文：30K 和 86K 各取了一段 `temperature=0` 输出，内容通顺切题；没有做长上下文的逐字对照。
- 未做：工具调用、流式中途取消、抢占、256K 实测、多日稳定性。

## 7. prefill（首 token 时间）现状

没有优化过，只有测量：

| 提示词 token | 首 token 时间 | 平均速度 |
|---|---|---|
| 7,687 | 1.8 秒 | 约 4,300 tok/s |
| 30,468 | 7.0 秒 | 约 4,350 tok/s |
| 57,091 | 16.9 秒 | 约 3,400 tok/s |
| 85,591 | 32.1 秒 | 约 2,700 tok/s |

越长越慢，从配置和代码看有三层原因（没有采过 prefill 的设备 trace，占比未知）：

1. 提示词按 2048 token 分块，每块都要对前面全部上下文做注意力，总时间带平方项。
2. prefill 的上下文页数桶按倍数跳（…255、509、1017、2047 页），超过 65K 的上下文按 130K 计算，超过 130K 按 262K 计算。
3. 每块对历史 KV 有 gather 和拼接两遍拷贝；掩码矩阵是 2048 ×（上下文 + 2048），4 个注意力组各建一份。

另有一处已定位未处理的断图：GDN 层 prefill 路径里的 `_preprocess_qk_l2norm` 被显式禁止编译。

## 8. 还可以做的方向

| 方向 | 场景 | 预期 | 把握 |
|---|---|---|---|
| 验证步的注意力改成整段相乘（像 prefill 用的融合内核那样），不再按页切成小矩阵 | 长上下文 decode | 30K 时剩下的 4.5 ms 可能减半 | 中，未验证 |
| prefill 上下文桶改细、掩码共用 | 长提示词首 token | 65K 以上可能减少两到四成 | 中，未验证 |
| drafter 5 层合并成更少的编译区域 | 短上下文 | 2–3 ms | 低，断图修复的经验表明这段未必在关键路径上 |
| 调整草稿 token 数 | 全部 | 不确定，只能实测 | — |

短上下文单路的理论下限是设备忙碌的 28 ms，现实目标大约是 42 → 38–40 ms。

# Gaudi2 Single-Card vLLM

面向 **单张 Intel Gaudi2（96 GiB HBM）** 的 vLLM 源码快照与本地适配工程，重点关注 Qwen3.5 系列的 FP8 推理、非 greedy 投机解码，以及主机到 HPU 的执行开销。

本仓库保存 **2026-10-14 从服务器读取的实际源码**，包含未提交的本地改动。它不是 Intel 或 vLLM 官方发行版，也不是“一键安装、所有功能均已验证”的稳定发行包。

## 项目来源

本项目基于 1Cat-vLLM-Gaudi 工程分支、[vllm-project/vllm-gaudi](https://github.com/vllm-project/vllm-gaudi) 硬件插件及 [vllm-project/vllm](https://github.com/vllm-project/vllm) 推理引擎。保留各组件原有 LICENSE、版权声明、文档及第三方许可；新增的单卡适配与采样扩展按所在文件的声明处理。

这是一次源码发布，不是向上游提交的 PR。部分本地适配和文档整理使用了 AI 辅助，仍需要人工审查与目标环境验收。

## 本地适配的主要方向

- **Qwen3.5 / Qwen3-Next 混合架构**：完整注意力、Gated DeltaNet、卷积历史及投机验证检查点的 HPU 路径。
- **FP8 推理**：Gaudi2 权重范围/布局处理、动态量化与 FP8 GEMM。模型 FP8 线性不等于所有算子或 KV 缓存都使用 FP8。
- **DFlash2 与 MTP**：包含本地草稿生成、目标验证、状态回滚和非 greedy 随机拒绝纠正实现。不同模型、投机宽度与 batch 的资格并不相同，不能任意互换。
- **CPU 提交链路**：decode 输入准备、注意力组路由、共享前缀准备、静态 guard 筛选及部分环境变量缓存。较新的 fast-decode 路径仍需完整验收。
- **OpenAI 兼容服务**：沿用 vLLM API；自动工具调用需启用相应选项并选择与模型模板匹配的 parser，本地配置使用过 `qwen3_xml`。
- **诊断入口**：保留有界计时和 profiling 支持。诊断配置不是性能推荐配置，不应在正式测速时默认开启全量 trace。

上述列表描述源码中存在的实现，不代表每个组合均经过完整模型、长上下文、并发、工具调用或取消/抢占验收。

## 我们优化了什么

| 项目 | 实际改动 | 状态与效果边界 |
|---|---|---|
| 非 greedy 投机解码 | 移植/适配本地 MTP 路径，接通 DFlash2 的目标验证、接受判断、拒绝纠正和状态回滚；保留主模型随机采样 | 已有非 greedy 短文本生成验收；不把草稿的确定性选词误称为主模型 greedy。完整模型概率/质量等价性仍需验证 |
| 随机拒绝纠正的 HPU 实现 | 增加 TPC 随机纠正/输出打包扩展与 Python 接线，减少纠正阶段的小算子及 host 往返 | 源码见 [native 采样扩展](native/mtp-sampling/) 和 [纠正入口](vllm-gaudi/vllm_gaudi/v1/sample/native_correction.py)；没有单独消融得到可归因的整体提速百分比 |
| DFlash 辅助特征感知分组 | 按辅助特征捕获边界合并目标 decoder 的编译区域；历史 v22 将 64 层组织为 19 组，仍完整执行每一层并保留 5 个捕获点 | 有短请求热性能改善，详见下表；没有跳层、降低精度或改成 greedy |
| CPU 交接与采样参数准备 | token list 交接、标量选择/采样准备缓存，减少部分重复准备 | 同进程热对照约 1% 变化，尚未证明稳定收益；小拷贝打包未启用，部分地址优化遇到 defragmenter 会回退 |
| Dynamo 静态 guard 筛选 | 对限定的参数、空 hook 和模块重复关系筛选 guard；保留输入、常量和运行时状态相关检查 | 已有 guard 回归；单独删少量参数 guard 未得到明显收益，不能跳过全部模块/运行时 guard |
| B≤2 的 GDN prepared 核路径 | 将投机验证分发从固定 B=1 扩展为可配置上限，并在本地资格范围设为 B≤2；保留接受检查点与合法写回槽位语义 | B1/B2 隔离数值测试通过；历史双请求每轮耗时有所改善，不代表任意 batch/短 query 都能使用该路径 |
| 较新的 decode 主机准备 | fast-decode 输入准备、注意力组路由、共享前缀准备及环境变量缓存 | 代码已在服务器快照中；v5 是诊断/smoke 配置，尚无统一验收后的净提速结论 |

FP8 GEMM、基础 RMSNorm/RoPE 和部分 GDN 核来自原有 Gaudi/1Cat 实现。本项目对这些路径做适配与接线，不将已有上游能力全部计作新写的优化。

## 优化效果：实测与未获收益的项目

以下是本地历史记录，**不是本次上传后重新测出的成绩，也不是当前 v5 配置的统一 benchmark**。测试硬件为单张 Gaudi2，目标为本地命名的 Qwen3.8-27B-FP8（配置属于 Qwen3.5 架构），TP=1 / PP=1。

### DFlash2 单流短请求

条件：43-token 故事 prompt、128 输出 token、`temperature=0.7`、`top_p=0.9`、`top_k=20`、`seed=123`、关闭 thinking、7 个草稿 token、无 profiler。这里的 token/s 是 **128 ÷ 请求总时间**，包含首 token 前时间，不是纯 decode 速度。

| 改动 / 对照 | 优化前 | 优化后 | 如何解读 |
|---|---|---|---|
| 辅助特征感知分组，v21 → v22 | 6.913 秒 / 18.52 token/s | 4.160 秒 / 30.77 token/s | 历史热请求耗时下降约 39.8%，吞吐约 1.66 倍；跨进程、少量样本，固定 seed 文本不同，不能称为严格数值等价的普遍收益 |
| CPU 交接＋采样准备，v25 同进程最后热对照 | 3.968 秒 / 32.26 token/s | 3.931 秒 / 32.57 token/s | 耗时下降约 0.95%；四条请求的正文和接受计数相同，但只有一组最终热对照，约 1% 差异可能是波动 |

v22/v25 的该短故事接受率约 **6.81%（41/602）**，86 轮输出 128 token，约 **1.49 输出 token/轮**。分组主要降低每轮执行开销，没有让草稿更准。历史同 prompt 的 MTP-7 热请求约 **3.855 秒 / 33.20 token/s**，因此不能声称 DFlash2 在这个负载上已经优于 MTP。

冷请求必须单独报告：v22 首条约 6.488 秒，v25 baseline 首条约 6.668 秒；不能把冷请求与后续热请求直接相除当作补丁收益。v22 初始化曾约 40.7 分钟，热速度改善不意味着预热也更快。

### 代码/技术类负载与 B2 GDN 路径

本地 v25 → Kiro v2 历史测速记录使用相同的代码/技术类 prompt、非 greedy 且关闭 thinking：900-token 单流约 **116–127 → 126–135 token/s**，两路合计约 **136–140 → 141–173 token/s**；记录中的 B2 每轮平均耗时改善约 **5–8%**。512-token 单流结果范围仍明显重叠，没有证据称所有单流请求都加速。

这些是历史记录中的测速口径，不与上面的 128-token 端到端结果混算。请求接受率、输出内容和运行条件会影响数字；未做 guard 与 GDN 分发两项的独立消融，不能把全部增益归给某一个核。也不将不同 prompt 的无投机基线与这些结果相除，宣传固定的“3–4 倍加速”。

### 最近预录候选：正确，但没有净提速

这部分是独立离线实验，**候选和私有框架没有包含在本次服务器源码快照中，也没有上线**。真实前 8 层（6 层 GDN＋2 层注意力）、完整 48 组状态池、B1/T8，接受长度 1/4/8 的输出与全部缓存严格匹配普通组；局部 CPU 回归共 321 项通过，不是本仓库全部测试通过。

| 完整状态池下的热组测试 | 普通执行 | 预录执行 |
|---|---:|---:|
| 提交 wall 中位数 | 0.923 ms | 0.862 ms |
| 整组完成 wall 中位数 | 5.613 ms | 5.797 ms |

8 次交替采样/路径，计时包含串行设备完成等待与事件退休。提交减少约 **6.7%**，但完成时间增加约 **3.3%**，所以不作为加速方案上线。这些是组级 wall 时间，**不是 HPU kernel 时间或模型 token/s**。单层固定输入池＋预录也未显示净收益；没有因“代码已实现”就默认启用。

仍需继续定位 GDN 检查点回写、FP8 动态量化与 CPU→设备提交链路，完成真实 runner 地址命中、长上下文、并发、工具/流式及取消/抢占验收。AIP-Util 低不是“没开 FP8”或“肯定在等 CPU”的单独证据，当前没有达到性能上限的证明。

## 使用前须知

1. 准备匹配的 Gaudi 软件栈及 SDK。不要为安装本项目随意刷固件、替换驱动，或让通用 CUDA 安装命令覆盖 HPU 版 PyTorch。
2. 分别阅读 [vLLM 核心说明](vllm-core/README.md) 和 [Gaudi 组件构建配置](vllm-gaudi/pyproject.toml)。这是多组件快照，仓库根目录不能直接作为单一 Python 包安装。
3. 自定义 FlashInfer-Gaudi/TPC 算子及 [随机采样扩展](native/mtp-sampling/) 需要按目标环境构建。仓库不包含服务器编译出的 `.so`、wheel 或 SDK 二进制。
4. 设置本机的模型目录、动态库路径、kernel 搜索路径及日志目录。源码中保留的部分默认路径来自原环境，不是可移植的部署承诺。
5. 先做组件数值验证，再做非 greedy 的短请求、工具调用和流式验收，最后比较同模型、同参数的热请求基线。不要直接开启所有实验 flag 或跳过预热后报告峰值。

请参考 [Intel Gaudi 文档](https://docs.habana.ai/en/latest/index.html) 与 [vLLM Gaudi 文档](https://docs.vllm.ai/projects/gaudi/en/0.26.0/index.html)；后者是单独的文档版本，不等于本快照的源码基线。

## 当前验证边界

服务器最新启动脚本指向 v5 **诊断 / smoke** 配置，含跳过预热、profiling 与 fast-decode 检查选项；本次只读取源码，不启动、停止或改动服务器服务。该配置没有被包装为默认生产启动器。

最近独立实验已验证真实前 8 层混合组的预录对照，以及完整 48 组 GDN 状态池的输出/缓存一致性；但 **预录没有显示端到端净提速**。对应未部署候选、私有重编框架和本地实验结果不属于这份服务器快照，未混入发布目录。

本次上传本身不构成新的模型测速或全量测试。没有宣称达到硬件性能上限，没有把低 AIP-Util 直接归因为 CPU 等待，也没有承诺投机解码必然优于普通解码。
